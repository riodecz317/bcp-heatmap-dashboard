# Brief: Executive BCP Dashboard — Remaining Accessibility & Visibility Gaps
- **Date:** 2026-08-25
- **Lane:** design
- **Target agent(s):** frontend-design-agent
- **Source prompt:** "We need to enhance the visibility and accessibility of the Executive BCP Dashboard for both light and dark mode users. The dashboard currently includes an Executive Summary, employee impact metrics, account and LOB breakdowns, a map section, a table, and a footer with office site details. Please provide design or code recommendations that ensure: Color Contrast & Readability: Use a neutral or adaptive color palette (e.g., grays, whites, and muted blues) that adjusts dynamically. Ensure text has a minimum contrast ratio of 4.5:1 against both light and dark backgrounds. Status indicators (Active, Monitoring) should be distinguishable by both color and shape/icon, not solely by color. Typography & Hierarchy: Use bold or semi-bold fonts for key numbers (e.g., 30 total employees, 14 active issues) to make them stand out. Ensure headings and labels are clearly differentiated from body text. Data Visualization: For the map and heat map, use colorblind-friendly palettes that also work in both modes (e.g., blue-to-orange gradients). Add hover or tooltip effects for clarity, and include text labels where possible. Table & Footer: Table rows should have alternating background colors that adjust per mode. Priority and Resolution columns should use icons or badges with consistent styling. Footer office site stats should be clearly separated with visual dividers. Responsive & Interactive Elements: Ensure that hover, focus, and active states are visible in both themes. Provide a manual toggle or system-preference-based switch for light/dark mode. Testing: Include a checklist for testing visibility under different lighting conditions and screen types."
- **Attachment:** none

## Goal

Close the real, verified remaining accessibility gaps in `Heatmap_Dashboard.html` (mirrored byte-identical to `index.html`) for both light and dark mode, without touching anything PR #11 already fixed, without regressing light mode, and without fabricating scope the user didn't ask for.

## Scope — real remaining gaps to implement

1. **Status dots on the map are color-only.** `L.circleMarker(...)` (around line 750) fills each province marker with `STATUS_COLOR[dotStatus]` (Active/Monitoring/Resolved) and nothing else distinguishes status at a glance — no icon, no shape, no permanent label (the tooltip only appears on hover, and the permanent `province-count-label` shows the total count, not status). This is the genuine "distinguishable by shape/icon, not solely by color" gap for the map.
   - Fix: add a status-differentiating visual to each marker that survives without hover — e.g., a small icon/glyph rendered via `L.divIcon` (reuse the existing `STATUS_ICON` characters already defined in this file) layered on or beside the circle marker, or a distinct marker outline/shape treatment per status. Do not just recolor; the fix must be perceivable in grayscale/without color.
   - Keep the existing hover tooltip (province name, total, per-status breakdown) — it's already good; just don't regress it.

2. **Province grid status-pills (`.status-pill`, line ~1012) are numeric counts under text column headers (Active/Monitoring/Resolved) with no icon.** This is borderline-compliant already (the column header labels the meaning), but for consistency with the Case Feed's icon+color+text pattern, add the matching `STATUS_ICON` glyph inline in each populated `.status-pill` next to the count. Treat this as a smaller, lower-priority polish item than #1 — the map is the actual color-only violation; this is consistency polish.

3. **No alternating row backgrounds anywhere.** Verified: no `nth-child`/`nth-of-type` rule exists in the stylesheet. `.province-row` and `.case-item` both currently render every row with the identical flat `var(--surface-2)` background — rows are only separated by `gap`/`margin-bottom` whitespace, not by color banding.
   - Fix: add a subtle odd/even background differentiation to `.province-row` and `.case-item` using the existing token system (e.g., alternate between `var(--surface-2)` and a new small-delta token, or `var(--surface-1)`/`var(--surface-2)` alternation) that stays theme-aware in both the light `:root` block and the dark `@media (prefers-color-scheme: dark)` / `:root[data-theme="dark"]` blocks. The difference should be a subtle, perceptible banding — not a new loud color, and must not reduce the contrast of any text/pill sitting on top of either row color below 4.5:1 in either mode.
   - Preserve the current rounded-corner, pill-per-row visual style; this is about adding row-to-row background variation within that style, not restructuring the layout into a literal `<table>`.

4. **Interactive hover states with hardcoded, non-theme-aware colors.** Found: `.exec-toggle-btn` (lines 284–292) uses hardcoded `color: #1E293B`, `background: #F3F4F6`, and hover `background: #E9EAEE` — none reference design tokens, so this control does not adapt for dark mode the way every other interactive element does. Also `.exec-top-row` (line 297) has a hardcoded `border-bottom: 1px solid #E5E7EB` instead of `var(--border)` or `var(--gridline)`.
   - Fix: convert these to theme-aware tokens (reuse existing tokens like `--surface-1`/`--surface-2`/`--border`/`--gridline`/`--text-primary`/`--row-hover`, or add narrowly-scoped new tokens with light + dark values following the existing pattern) so the button's default, hover, and focus states are all clearly visible and consistent with the rest of the dashboard in dark mode.
   - This is the concrete instance of the user's "hover, focus, and active states visible in both themes" ask — audit these two selectors first, and if you find other hardcoded (non-`var(--...)`) colors on interactive elements outside the KPI/status system while doing this pass, fix those too, but do not re-touch anything already covered by PR #11's documented fixes.

5. **Footer office-site chips have no visual divider between them.** `.office-chip` (lines 470–478) renders each office as its own rounded pill with `background: var(--gridline)` and the chips sit in a flex row with only an 8px gap — there is no explicit divider (rule line, border) separating them, and no divider separating the "Office Sites" label from the first chip.
   - Fix: add a lightweight visual divider — e.g., a thin `border-right` or `::after` rule element using `var(--border)`, or increase separation between the label and the chip row — using existing tokens only. Keep this modest; the chips are already individually distinguishable by their own pill background, so this is a refinement, not a rebuild.

6. **Manual light/dark toggle does not exist.** Verified: theme currently switches only via `@media (prefers-color-scheme: dark)`; there is a dead `:root[data-theme="dark"]` CSS hook and a dead `:root:where(:not([data-theme="light"]))` guard in the CSS, but no JavaScript anywhere in the file ever sets `data-theme` on any element, and there is no toggle control in the markup (only `execToggleBtn`, `labelToggle`, `sortToggle` exist, none of which are theme-related). This is a real, well-defined new feature to build:
   - **UI control:** add a toggle button/switch in the top header/brand bar area (near `.brand-block`, alongside the existing header controls) — a simple icon button (sun/moon or similar) is sufficient; it does not need to be a segmented 3-state control unless trivial to add.
   - **Behavior:** clicking cycles between light and dark, setting `data-theme="light"` or `data-theme="dark"` on `<html>` (or `:root`'s element). Both explicit states already have matching CSS (`:root[data-theme="dark"]` block already fully populated; a `:root[data-theme="light"]` explicit override is not needed since removing/absence of `data-theme="dark"` combined with the `:not([data-theme="light"])` guard on the media query should fall back correctly — verify this interaction works for a user whose OS is set to dark but who manually picks light).
   - **Persistence:** store the user's explicit choice in `localStorage` (follow the existing pattern already used in this file for `EXEC_COLLAPSE_KEY`, i.e. wrap `localStorage` calls in try/catch since storage may be unavailable) and re-apply it on load before/as the page renders, so there's no flash of the wrong theme.
   - **Default:** if no stored preference exists, defer to `prefers-color-scheme` as today (i.e., don't set `data-theme` at all until the user actively toggles).
   - Ensure the toggle control itself has a visible, theme-aware hover/focus state (ties back to gap #4) and an accessible label (`aria-label` reflecting current/target state).

## Map & heatmap color: reinterpretation of the user's literal suggestion

The user asked for "colorblind-friendly palettes... e.g., blue-to-orange gradients" for "the map and heat map." Do **not** implement this literally. There are two distinct color-encoded elements here and they need different treatment:

- **Province choropleth polygon fill** (`SEQ` array, `--seq-0`…`--seq-4` tokens, used in `L.geoJSON(feats, { style: { fillColor, ... } })` around line 739): this is a genuine sequential/magnitude encoding (province total employee count), and it already uses a single-hue pale-to-saturated scale (currently red-based) rather than a rainbow — this is a reasonable existing choice. Confirm/validate it, don't replace it with an unrelated diverging blue-to-orange scheme unless validation shows it fails.
- **Map marker (`circleMarker`) fill and the province-grid `.status-pill` / Case Feed colors** (`STATUS_COLOR`): these encode a **categorical** variable (Active/Monitoring/Resolved), not a magnitude. A gradient (blue-to-orange or otherwise) would misrepresent categorical status as if it were an ordered/continuous scale and must not be applied here. The real fix for these is #1 and #2 above (icon/shape redundancy), not a new palette.

Action: use the `dataviz` skill's `validate_palette.js` (referenced in this file's own code comments, lines ~44–45, from earlier work on this project) to validate the **existing** `--status-good` / `--status-warning` / `--status-critical` triad and the existing `--seq-0..4` sequential scale for CVD-safety and contrast, in both light and dark values. If validation passes (as the inline comments already claim for the status triad — `ΔE 2.0` protanopia vs. `14.8` normal, already computed for `--status-warning` vs `--status-critical`), do not change those hues; only proceed with a palette change if validation surfaces a genuine failure. **Note for the executor:** this brief's author could not locate `validate_palette.js` inside this repo (`ShadowRealm - Heatmap`) via file search — it is referenced only in code comments from prior work, implying it lives in a shared/global `dataviz` skill outside this repo's tree. Confirm its actual location before relying on it; if it truly cannot be found, fall back to the same manual WCAG relative-luminance/contrast math already used and documented for PR #11, and say so explicitly in your output rather than skipping validation.

## Acceptance Criteria

- Map markers convey Active/Monitoring/Resolved status via more than color alone (icon, shape, or permanent label), verifiable by viewing the dashboard in grayscale/desaturated mode.
- Province-grid `.status-pill` elements show the existing `STATUS_ICON` glyph alongside the count.
- `.province-row` and `.case-item` rows show a perceptible, theme-aware alternating background (odd/even), correct in both light and dark mode, with no text/pill on either banding falling below 4.5:1 contrast.
- `.exec-toggle-btn` (default, hover, focus) and the `.exec-top-row` divider use only design tokens (no hardcoded hex) and are clearly visible in both light and dark mode.
- `.office-chip` items in the footer have a clear visual divider between them and between the "Office Sites" label and the first chip.
- A manual light/dark toggle control exists in the header, correctly sets `data-theme` on load and on click, persists the user's explicit choice via `localStorage` (with try/catch), and falls back to OS `prefers-color-scheme` when no explicit choice has been stored.
- The toggle control itself has a visible, theme-aware hover/focus state and an accessible `aria-label`.
- The existing status color triad and sequential choropleth scale are validated (via `validate_palette.js` if locatable, else documented manual contrast/CVD math) rather than replaced outright; any palette change is justified by a documented failure, not aesthetic preference.
- No changes to `bcp_data.json`, `RAW_DATA` shape, or files outside `Heatmap_Dashboard.html`/`index.html` (kept byte-identical to each other).
- No regression to any of PR #11's already-fixed contrast pairs (spot-check KPI values, province headers, status-soft pill backgrounds, hatch-track, `--status-warning` in dark mode).
- Deliverable includes a short manual test checklist covering: light mode/desktop, dark mode/desktop, OS set to dark + manual override to light (and vice versa), and a grayscale/desaturated pass to confirm status indicators remain distinguishable without color.
